## 二、项目名称怎么写

**较差写法：**
> ❌ 客服聊天机器人项目
> ❌ 基于大模型的智能问答系统
> ❌ Agent 知识库管理工具

**较好写法：**
> ✓ **自进化 Agent 教学演示系统：Skill 知识库的失败驱动动态优化**
> ✓ **基于契约式设计的 Agent-Reviewer-Evaluator 三角协作原型**
> ✓ **Hermes Nudge 机制 + GEPA 思路的 Agent 自进化原型**

关键词："自进化"、"失败驱动"、"契约式设计"、"Nudge 机制"——在当前 （2025-2026）AI 岗位招聘里有明显辨识度。

## 三、按岗位方向写法

### 3.1 算法工程师 / LLM 方向

核心卖点： **不是调 Prompt，不是接 API，是设计 Agent 自改进闭环**。

> **自进化 Agent 教学项目** · 全栈开发 · 2026.05
> - 参考 Anthropic Hermes Nudge 机制与 Stanford DSPy GEPA 算法，设计一套 Agent
>   知识库（Skill）的运行时动态优化闭环。主 Agent 在对话中失败 → 失败样本注入
>   后台回顾 Agent → 输出最小必要的 create/patch 操作 → 更新 Skill → 后续应答
>   直接使用新 Skill，形成"失败即训练"的自改进链路
> - **契约式设计**：Agent 能答即答具体结论、不能答仅说"需要联系人工客服"；
>   Evaluator 据此契约一票否决 + required/forbidden 关键词检查，失败原因三分类
>   互斥（推脱 / 缺关键词 / 禁止词），无歧义
> - **核心算法**：设计 Skill 版本追踪三层持久化（活动版 + 历史 JSON + 每版独立
>   Markdown 快照），支持跨版本问答对比。Reviewer 严格最小改动原则（仅修复观察
>   到的失败、按频次只修 1~2 类，留出进化梯度）；块内全对时完全跳过 Reviewer
>   调用
> - **实验设计**：8 块类别纯化演示脚本（失败信号清晰），基线 22% → 进化后
>   70-90%，每轮 Nudge 的 create/patch 对应本块失败的归因
> - **评估器实现**：关键词匹配 + 数字千位归一化（`4,000 → 4000`）+ 否定前置
>   检测（`不可直接取消` 不误伤 `直接取消`），保证规则评估在 90% 准确率天花板内
>   稳定运行
> - **技术栈**：Python / OpenAI SDK / DeepSeek API / FastAPI / SSE / Vanilla JS

### 3.2 后端工程师 / 全栈方向

核心卖点： **从协议设计到生产部署的完整工程经验**。

> **自进化 Agent Web Demo 系统** · 全栈开发 · 2026.05
> - 从 0 搭建 AI 教学演示系统，后端 Python/FastAPI + 前端单文件 HTML（无 CDN
>   依赖、离线可用），支持课堂步进式演示和无 UI 批处理两种模式
> - **服务端**：FastAPI 应用含 SSE 流式推送（3 个长连接接口 + 3 个 REST），
>   每次 LLM 调用经 `asyncio.to_thread` 非阻塞化，实时流式输出每题应答；全局
>   状态管理支持"重置到初始态"幂等还原
> - **前端**：三栏响应式布局 + 多级折叠卡片（Q&A、Nudge 事件、Skill 版本历史
>   均可独立折叠）；smartScroll 机制仅当用户已在底部附近才跟随，避免打断手动
>   翻阅
> - **数据持久化**：设计三层 Skill 版本追踪（活动版 + 完整历史 JSON + 每版
>   独立 .md 快照），支持按版本号回溯任意历史状态；evolution_log.json 含
>   question_comparison 字段，可查任意问题在所有评估点的答案变化
> - **关键工程细节**：
>   - 诊断 CSS Grid + Flex 嵌套下 overflow:auto 失效（全链 min-height:0 修复）
>   - 修 LLM 数字千位分隔符导致的评估误判（lookaround 正则归一化）
>   - 修基线/最终评估 DOM id 冲突（事件带 run_id 字段分开前缀）
>   - uvicorn 开发模式 `--reload` 自动加载

### 3.3 AI 产品经理 / 解决方案方向

核心卖点： **懂 Agent 机制本质 + 能把复杂概念讲清楚**。

> **自进化 Agent 教学系统设计** · 产品设计 + 原型开发 · 2026.05
> - 主导设计一套面向课堂教学的 Agent 自进化演示系统，围绕"Skill 不是 RAG 文档、
>   演进不是话术调整"这一核心教学点，用可视化步进方式展示 Hermes Nudge 机制的
>   底层原理
> - **场景选型**：对比数学题/代码生成/真实客服数据四类备选，最终选定 **虚构电商
    > 政策**场景——基础 LLM 准确率天然 ≈ 20%（坦诚推脱），进化空间大，Ground
>   truth 完全可控，既能真实演示 Skill 价值又规避数据泄漏风险
> - **契约式设计的产品价值**：Agent 行为规范（能答就答、不能答就说联系人工）+
>   Evaluator 据此硬性判定，三种失败原因互斥清晰——学生看准确率分类表就能判断
>   下一步该做什么（推脱多 → 需要新 Skill；缺关键词多 → 需要 patch）
> - **教学流程设计**：80 题拆成 8 个纯类别块（基础退款 → 数字商品 → VIP 陷阱
>   → 物流 → 促销...），每块对应一次 Skill 进化触发点； **块内全对自动跳过
    > Nudge**，学生看到"失败 → 诊断 → 修 Skill → 再测"的清晰因果链
> - **可视化设计**：左侧准确率记录（可定量对比），中间对话流（可定性观察），
>   右侧 Skill 库（可查看结构变化）；Nudge 触发时紫色卡片，跳过时绿色卡片，
>   两类视觉对立让学生直观感受"进化触发条件"
> - **实验设计**：基线全量 60 题，每次 Nudge 后 Probe 30 题固定集，最终全量 60
>   题——三级评估保证跨版本可比且成本可控

## 六、面试常见问题（基于本项目）

### 6.1 技术原理层

**Q：Skill 和 RAG 有什么本质区别？**
A：RAG 是原始知识的扁平化存储，每次查询基于相似度检索片段插入 Prompt，知识库 本身不变。Skill 是 Agent 持有的带条件分支的操作
SOP，Agent 根据对话失败 **主动 修改** Skill 文件，让下次应答更准。最大差异在于：RAG 的知识库是 **只读的**， Skill 是
**可写的**；Skill 演化的本质不是"改话术"而是"补决策分支"。

**Q：Nudge 机制为什么要放在"响应之后"？**
A：Hermes 文档里给的答：放在响应交付后是为了 **不和用户任务竞争模型注意力**。 每 N
次调用做一次反思，既给了反思机会又不拖慢主流程。本项目简化成"每块 10 题 后统一反思"，教学上更干净——学生能清楚看到一个完整块的失败信号如何驱动一次
Nudge。

**Q：为什么不把所有对话历史都传给 Reviewer，而是只传失败样本？**
A：实测发现 LLM 作 Reviewer 时会把对全量对话的"美学感知"也带进来——觉得 答对的对话"还不够周到"、现有 Skill
"还不够全面"，于是对完全答对的块也产生 改动建议。隔离只传失败后：

1. Reviewer 只针对客观失败做改进，不做主观美学优化
2. 块内全对时完全跳过 Reviewer 调用，节省成本
3. 触发条件清晰可解释：学生能精准看到"因为这 N 条失败，所以做这 M 个改动"

**Q：你为什么选规则评估而不是 LLM-as-judge？**
A：三个原因：①成本（一次完整实验约 0.2 元，LLM-as-judge 要 ~5 元）； ②可复现（规则是确定性的）；③教学透明（规则简单，学生能看懂）。代价是
≈10% 的误判上限，用 **契约式设计**把"不确定"从语义判断转成子串检查，大幅 降低了规则评估的误判率。

### 6.2 设计决策层

**Q：Agent 不确定的时候说什么？为什么用这个契约？**
A：约定 Agent **仅回答一句**"需要联系人工客服"。好处：

- 评估器可以用 "联系人工" 子串一票否决作为 Skill 未覆盖的硬信号
- Agent 不会答对了还加推脱尾巴模糊判定
- 三种失败原因（推脱 / 缺关键词 / 禁止词）互斥，分布直接反映 Skill 质量

**Q：为什么主 Agent 每次应答不带 conversation_history？**
A：评估独立性。每题的对错应只反映当前 Skill 库的能力，不应被"上一题的回答"
污染。对应 Hermes 的机制——主 Agent 有短对话上下文，但 Reviewer 接到的是 独立的 messages_snapshot。本项目简化成每题全独立，既保证评估干净又方便量化。

**Q：为什么 Reviewer 被约束"只修 1~2 类"？**
A：为了保留 **进化梯度**。如果 Reviewer 一次把所有失败都修完，后续块就没
进化空间，曲线变成"一次跃升"而非"每块小幅改进"。学生看到的教学节拍会消失。 限制为 1-2 类后，block 2 的 Nudge 专注修数字商品、block
3 修 VIP 退款，每块 的进化轨迹对应清晰教学节拍。

**Q：为什么 Probe Eval 用固定 30 题？**
A：跨版本可比性。N 次 Probe 如果每次随机，难度波动淹没 Skill 改进信号。 用固定 30 题，N 次的准确率可直接画成进化曲线。代价是
Probe 和 demo 脚本有 重叠，但 Agent 无状态（每次独立应答），重叠不会造成"记忆作弊"。

### 6.3 工程设计层

**Q：如果 Reviewer 返回一个错误的 Skill 操作（比如删了重要规则），怎么办？**
A：这是"skill drift"问题。Hermes 原型靠 skills_guard 做安全扫描，本项目 为了简化没实现。真实生产要三种机制叠加：①版本历史可回滚（本项目已做）；
②patch 操作做 syntax validation；③关键规则用"不可删除"标注。本项目演示 过一次 drift：给 refund 加 VIP 分支后普通用户运费反而答错——这正是
GEPA 阶段要解决的问题。

**Q：evolution_log.json 怎么设计的？**
A：三个核心字段：

- `skill_snapshots`：每个 Skill 的完整版本时间线
- `eval_runs`：每次评估的汇总（准确率 + 分类）+ 对应 Skill 版本号
- `question_comparison`：每道题在所有评估点的答案历史

`question_comparison` 是教学核心——学生能看到"Q11 在基线时答'超过 30 天 不可退'（错），Nudge 后答'银卡 60
天可退'（对）"。设计时特意把它放在顶层 字段，查询复杂度 O (1)。

**Q：数字千位分隔符 "4,000" vs "4000" 怎么处理的？**
A：先归一化。正则 `re.sub(r"(?<=\d)[,，](?=\d)", "", text)` 一次性去除所有 夹在数字之间的英文/中文逗号，包括嵌套场景如
"1,234,567"。好处是 evaluator 核心匹配逻辑不用关心分隔符，关键词本身用 "4000" 即可。

**Q：为什么基线/最终评估的问题曾经点击无法展开？**
A：DOM id 冲突 bug。Baseline 和 Final 都用 `st.phase` 判断 runId 前缀，但流 开始时客户端 phase 还没更新，fallback 到
'eval'，结果两阶段都用 `q_e1..q_e60`
作为 id。修复：SSE 事件直接带 `run_id` 字段，前端用 `q_b{id}` / `q_f{id}`
分开前缀，永不冲突。

## 七、不建议写的内容

❌ 不要写"使用最新 GPT-4/Claude 4 实现"——本项目是教学 Demo，用 DeepSeek 就够 硬凑"最新模型"反而像在堆关键词

❌ 不要写"实现完整 GEPA 算法"——本项目只做运行时 Nudge，没做遗传+帕累托。写
"受 GEPA 启发"而不是"实现 GEPA"

❌ 不要写"彻底解决 Agent 幻觉"——本项目演示了 Agent 在某些情况下仍会幻觉或 强先验偏见（如白卡 VIP 陷阱），不要夸大

❌ 不要写"部署到生产"——教学 Demo 就是 Demo，真实生产要考虑并发、多用户、 权限、审计等本项目未覆盖的问题。写成"生产级原型"更诚实

❌ 不要写"实现 90%+ 准确率"——准确率依赖 Skill 演化的彻底程度，而且规则评估 的 ≈10% 误判上限客观存在。写"在受控场景下验证了
Skill 自进化的有效性"更 恰当

## 八、结语

项目本身做的是一件小而完整的事： **把 Hermes 的一个核心概念（Skill 自进化）
在低成本场景下完整演示出来，并在工程层面解决了若干原设计的隐蔽问题**。

简历写法围绕这个核心价值：

- 不是"我会用 LLM API"（门槛太低）
- 不是"我做了另一个问答系统"（同质化）
- 是"**我理解 Agent 自学习机制的原理，并能用代码完整实现 + 量化验证 + 诊断并解决原设计的问题**"

这在当前阶段的 AI 岗位市场上是明显的差异化卖点。
